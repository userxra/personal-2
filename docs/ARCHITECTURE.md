# Architecture

## Overview

```
Browser (React SPA) ──/api──▶ Express API ──firebase-admin──▶ Firestore + Cloud Storage
        ▲                          │
        └──── SSE /api/events ◀────┘   (Redis pub/sub when REDIS_URL is set)
```

- Dev: Vite (`client/vite.config.ts`, port 5173, strict) proxies `/api` to `localhost:4000`.
- Prod: Netlify serves the static client and rewrites `/api/*` to the Render service (`netlify.toml`), so the browser sees one origin and cookies are first-party (`SameSite=Lax`).
- `shared/types.d.ts` holds every API request/response type. Both apps `import type` from it by relative path (`tsconfig` of each app includes `../shared`). It contains no runtime code.

## Server (`server/src`)

| Dir                  | Role                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.ts`, `app.ts` | Boot, middleware order: request logger, helmet, CORS (`CLIENT_ORIGIN`, credentials), JSON (1 MB), cookies, `/api` rate limit (300/min), routes, error handlers |
| `config/`            | `env.ts` (zod-validated env, throws on invalid), `firebase.ts` (lazy init; `db()`, `bucket()`)                                                                 |
| `routes/`            | One file per feature, mounted in `routes/index.ts`. Validation with zod (`middleware/validate.ts`), then call a service                                        |
| `services/`          | Business logic. Receives a `Ctx` (user id, client id) and calls `notifyChange` to push SSE events                                                              |
| `data/`              | Firestore/Storage access only, one `*Repo.ts` per collection                                                                                                   |
| `middleware/`        | `auth`, `validate`, `rateLimit` (Redis-backed if configured), `upload` (multer), `requestLogger` (pino), `errorHandler`                                        |
| `permissions.ts`     | The only place roles/permissions are decided (`can`, `canModifyUser`, `requirePermission`)                                                                     |
| `lib/`               | errors, tokens, cookies, password, text (search term building), logger, redis                                                                                  |

Mounted API prefixes: `health auth users journal writing notes links tasks projects books documents income expenses subscriptions money-ideas versions reviews moments vault inbox me events`.

### Auth

- Access JWT 10 min (cookie path `/`); refresh JWT 14 days (cookie path `/api/auth`), single-use and rotated; its `jti` is a doc in `refreshTokens`.
- Request auth reads no DB. A disabled user is locked out at next refresh. Login/register are rate limited (20 per 15 min).
- Roles: `user`, `admin`, `superadmin`. Content is under `users/{uid}`, so nobody (admins included) can reach another user's content through the API. **There is no admin UI in the client**; user management exists only as API routes (`/api/users`).

### Realtime

`routes/events.routes.ts` streams SSE with a 25 s heartbeat. Services emit `ChangedEntity` events; `client/src/hooks/useRealtime.ts` maps them to TanStack Query invalidations. Without Redis, fan-out is in-process (single instance only).

## Firestore model (everything under `users/{uid}/`)

Collections: `journal`, `writing`, `notes`, `versions`, `tasks`, `projects`, `books`, `documents`, `income`, `expenses`, `subscriptions`, `moneyIdeas`, `reviews` (id = Monday of the week), `moments`, `vault`, `links`, `inbox`, `documentFolders`, `activity` (id = local date). Meta docs: `meta/{prefs,tags,topics,folders,library,income,expenses,vault,stats,activity}` (`meta/folders` holds the old name-based folder counts and is no longer written; `meta/library.foldersVersion = 2` marks the one-time folder migration as done). Global: `users`, `refreshTokens`.

Patterns to keep:

- **Running totals** (`meta/income`, `meta/expenses`, tag/topic counts) use `FieldValue.increment` inside the same transaction as the change.
- **Journal ordering** uses `sortKey = date|createdAt|id` (one `orderBy`, cursor pagination). Lists `select()` away bodies.
- **Search**: each doc stores `searchTerms` (accent-folded words + 3+ letter prefixes); one `array-contains` query per collection on the longest word, remaining words checked in memory.
- **Conflicts**: entries carry `rev`; a stale save gets `409 EDIT_CONFLICT`. Only content changes bump `rev`.
- **Versions**: snapshot written inside the entry update transaction (at most every 30 min while editing).
- **Links**: docs `{from: "type:id", to: "type:id"}`, queried both ways. Library folders are `folder:id`; deleting a folder removes its links. Folders have no stored `searchTerms`: search matches folder names in memory from one read of the folder list.
- **Files**: Storage at `users/{uid}/documents/{id}/file` (+ `thumb.webp`) and `users/{uid}/vault/{id}.bin`; only served through the API (with HTTP byte ranges, so video can seek). Library files are immutable and served with a one-year `immutable` cache; logout clears the browser cache (`Clear-Site-Data`).
- **Folder sizes** (`GET /api/documents/folders/sizes`, `folderService.folderSizes`): reads every file's `folderId` and `size` (`select()`, one small read per file) and adds them up through the folder tree. A filtered `sum()` aggregation would be cheaper but may need a composite index, so it isn't used. The client caches the result for 10 minutes and refreshes it on any library change.
- **Library folders**: `documentFolders/{id}` = `{name, parentId}` (null = top level); each document has `folderId` (null = top level). Listing a folder is two equality queries (`parentId ==`, `folderId ==`); the client loads all folders once and builds the tree (breadcrumbs, move picker). Moving changes only these pointers, never Storage paths or ids. Recursive delete and usage counts use `folderId in [...]` in chunks of 30 (and a count aggregation). Sibling folder names are unique (case/accents ignored), nesting is capped at 20 levels, and moves into a folder's own subtree are refused, all checked in `folderService`.
- **Folder migration** (`services/libraryMigration.ts`): files used to carry a free-text `folder` name. The first library request per user turns each distinct name into a top-level folder (deterministic id, so re-runs are no-ops), sets `folderId` on every file and rebuilds its search terms. Additive only: the old `folder` field is left in place.
- Project task counts use a Firestore count aggregation (`GET /api/projects/task-counts`).
- **Profile statistics** (`services/profileService.ts`, `data/statsRepo.ts`): item counts, task/note-type counts and library size come from `count()`/`sum()` aggregation queries, one aggregation per query (several in one query would need a composite index; about 50 queries, one read per 1,000 documents each), so they always match the data. No running counters.
- **Written text**: journal, writing and note docs, weekly reviews, moments, books, projects and money ideas store `textWords`/`textChars`, recomputed by every save from one definition (`services/textStats.ts`, counting in `lib/text.ts#textStats`). Older documents are counted once by a backfill on the first profile visit (`meta/stats.textVersion`; writes use a `lastUpdateTime` precondition, so a document saved meanwhile is skipped). Bumping `TEXT_VERSION` recounts everything; `POST /api/me/profile/recount` does it on demand.
- **Active time** (`services/activityService.ts`, `data/activityRepo.ts`): tabs send visible stretches (`POST /api/me/activity`, `{id, seconds ≤ 120, ago, date, section?, visit?}`, up to 60 per request). One transaction updates `activity/{date}` (seconds, sessions started, first/last, `sections.{key}` = seconds/visits/lastAt) and `meta/activity` (totals, `months` with per-section seconds/visits and action counts, `sections` all-time, `sectionsSince`, `actions` all-time, the last 20 sessions, merged stretches of the last 15 min to remove overlap between tabs/devices, last 200 beat ids for idempotency). Overlapping time goes to the section of whichever stretch arrived first; a visit counts only if its stretch added time. Sessions split on a 30-minute gap. Recount rebuilds every total (time, sections, actions) from the day docs, keeping `sectionsSince`. Vault usage briefly recorded by the first release is erased from the days and totals on the next profile load (`withoutVault`, flag `vaultUsageRemoved`); a `section: 'vault'` beat from an old tab is accepted and dropped.
- **Usage actions** (`activityService.recordAction`): services call it after a successful create/edit (entries, tasks, projects, books, files, folders, money, moments, reviews, links, Quick Capture; never the vault). It stores the item id under `activity/{date}.actions.{action}` (date from the `X-Local-Date` header when within UTC−14..+14 of now, else the server's UTC date) and bumps `meta/activity.actions` and the month, in one transaction; an id already there, or an edit to an item created that day, adds nothing. An in-process set skips the transaction for ids already counted (autosaves). Failures are logged, never thrown. `GET /api/me/usage?from&to` (≤ 400 days, one read per stored day) returns the days for the profile's history.

## Client (`client/src`)

- `main.tsx` provider order: PersistQueryClient, Theme, Router, Toast, Confirm, Auth, Vault, UI, then `App`.
- `App.tsx`: routes; Home, Journal, Tasks and the editor are in the main bundle, every other page is `lazy()`, and `AppShell` fetches all their code in the background once the browser is idle (`requestIdleCallback`, a 1.5 s timeout where it is missing), so later navigation doesn't wait for it. `RequireUser`/`GuestOnly` guard auth. While the initial `/auth/me` check runs, `RequireUser` shows `ShellFrame` (sidebar + mobile nav) with a `PageSkeleton` if this device was signed in last time (a yes/no flag in localStorage, `auth:signed-in`, set and cleared by `AuthContext`); otherwise nothing, so the login page doesn't follow a flash of navigation. `AppShell` wraps signed-in pages (sidebar, mobile nav, capture/search dialogs, task detail host) and holds the `Suspense` boundary so the shell stays during page loads.
- Entry editor: `EditorPage` uses the formatted `RichEditor` (Tiptap, lazy chunk, preloaded with the pages) or the plain `MarkdownEditor`; both implement `MarkdownEditorHandle`, so the format bar, file/web link pickers and unlinking work the same with either. Bodies are Markdown either way (see decision 22).
- Loading states: a page renders its real frame (header, tabs, forms, section headings) at once and puts skeletons (`components/ui/Skeleton.tsx`) only where data is pending, shaped like the content they stand for, so nothing jumps when it arrives. Skeletons show only on a first load (`isLoading`, i.e. no cached data); background refetches keep what is on screen. A section that depends on two queries waits for both (Projects waits for open tasks so it never shows "no next step" first; journal/writing/ideas lists wait for tags, whose filter row sits above them; money figures wait for the base currency). Empty and error states replace skeletons as before.
- `features/`: `capture documents entries home inbox library links me money profile projects reviews search tasks timeline vault`.
- Active time: `features/profile/activityTracker.ts`, started by `AppShell` for the signed-in user. Counts while `document.visibilityState === 'visible'` (no idle timeout; a >20 s gap between 5 s ticks means the device slept and isn't counted), saves the current stretch to `localStorage` (`activity:<id>`) every tick, sends every 60 s and on hide/`pagehide` (`keepalive`), and resends anything left over (crash, offline, sign-out) on the next visit. Beats are tagged with the user id and dropped after 7 days. Each beat is one section (`lib/sections.ts`, from the pathname; `AppShell` passes it in; `/vault` gives null and nothing is counted there) and moving to another section seals it; sealed beats go out about once a minute. A visit flag goes on the first beat after entering a section from another, or after 30+ minutes away; `localStorage.activityLastSeen` (section + time, written only once a kept stretch has time) lets reloads, quick remounts and other tabs continue a visit instead. `apiFetch` sends `X-Local-Date` with every request. The profile's usage history (`features/profile/usage.ts`, `UsageHistory.tsx`) fetches one window of days (`usageWindow`, about three months) and computes every period from it. Each holds its pages, API hooks (`api.ts`) and parts.
- Installed app (PWA): `vite-plugin-pwa` (`generateSW`, `registerType: 'prompt'`) precaches the built files and serves `index.html` for navigations (not `/api`). `lib/appUpdate.ts` applies a new version (a reload) only if it is found in the first 5 s after launch and nothing holds work, or on pull to refresh; otherwise it waits for the next launch. It also checks for a new version when the app returns to the foreground.
- Query cache on the device: `lib/queryPersist.ts` stores the TanStack Query cache in IndexedDB (`idb-keyval`, key `query-cache`) for up to a week (`gcTime` matches), with the deploy commit as buster (`__BUILD_ID__` from `vite.config.ts`: Netlify's `COMMIT_REF`, else `git rev-parse HEAD`). Not stored: the vault, entries open in the editor, versions, search and status queries, a signed-out `me`. It is removed on sign-out, when `/auth/me` finds no session, and never restored without the `auth:signed-in` flag (the tokens are httpOnly cookies the page can't see). `me` is stored so the app opens offline, but is always re-checked on launch.
- Pull to refresh (`components/shell/PullToRefresh.tsx`, mounted by `AppShell`): on the document at scroll top only; it takes the gesture from the first downward move (non-passive `touchmove`), pushing back up cancels, and a release past the trigger refetches active queries or applies a waiting app update. Off in editors, while a dialog is open, while a field is focused, and while anything registered with `lib/busy.ts` (`useHoldWork`) has unsaved work (vault editor, `AutoSaveText`).
- Miniapps: apps live in `client/miniapps/<id>/` (manifest `index.ts`, `App.tsx`, optional `Widget.tsx`), found at build time by `features/miniapp-host/registry.ts` (`import.meta.glob`). They may import only `react`, `lucide-react`, their own files and the toolkit `@miniapp/sdk` (alias for `features/miniapp-host/sdk`: `defineMiniapp`, `useAppData`, `useMiniapp`, dates, toasts, a few UI pieces); ESLint enforces that, and that `client/src` never imports `client/miniapps`. The host (`features/miniapp-host`) has the miniapps screen with wallpaper (icons and widgets arranged by dragging: `useDragReorder.ts`, pointer events and a FLIP animation, no library; the arrangement is `settings.layout` and `settings.folders`, see `layout.ts`; an icon held over another makes a folder, `FolderView.tsx`; badges from each app's `badge(data, now)` over its cached data, `badges.ts`; live icons from an app's `liveIcon(data, now)` over the same cache, inside `MiniappIcon` when it is given the app; an app with `fullScreen` is shown without the frame's title bar and may colour the status bar with `useStatusBarColor` (`sdk/statusBar.ts`); the opening animation is a layer on `document.body`, `launch.ts`; a picture wallpaper's brightness is measured once on a small canvas and cached per picture, `pictureTone.ts`, and decides label colour and the bottom bar's tint, `navTone.ts`), the Store, the wallpaper picker, the frame an app runs in (context, Suspense, error boundary) and Home widgets. `useAppData` updates optimistically, saves in the background with a rev check (on a conflict it re-applies the updates on top of the newer data), keeps unsaved data in `localStorage` while offline, and uses the app's `merge` after a reload. Server: `/api/miniapps` stores install state and one opaque JSON per app in `users/{uid}/miniapps/{appId}`, and screen settings (wallpaper, app order, `layout`: tile keys such as `teeth`, `store`, `widget:teeth`, `widget:clock`, `folder:<id>`, null until first arranged; `folders`: id to name and icon keys; PUT `/api/miniapps/layout` drops folders no longer placed) in `meta/miniapps` (pictures in Storage, re-encoded by sharp).
- `lib/apiFetch.ts`: the only fetch wrapper (JSON/FormData/raw bytes, silent single refresh on 401, `ApiError`, `X-Client-Id`).
- `lib/keys.ts`: query keys; other keys are defined next to their hooks (e.g. `projects/api.ts`). Invalidate consistently when a mutation touches related data.
- Drafts: the editor mirrors text to `localStorage` (via `lib/storage.ts`, never throws) so closed tabs and offline edits recover. **Vault content and locked entries are never stored locally.**
- Locked entries (journal, writing): `features/entries/EntryLockContext.tsx` holds the entries key in memory once opened with the PIN (`lib/entryLockStore.ts`; decision 28: device box + salt in IndexedDB `notebook-entry-lock-v2`, server half from `POST /api/entry-lock/unlock`, 5 tries counted on the server in `users/{uid}/pinDevices/{deviceId}`; the entries key itself is in `users/{uid}/meta/entryKey`, encrypted with the vault key; first use on a device needs the vault passphrase). Sealed boxes carry the key id (`k`); boxes without it were sealed with the vault key and are re-sealed by `migrateEntries.ts` through `POST /api/{journal,writing}/:id/reseal`. `useEntryEditor` takes an `EntryCipher`: saves send `sealed` (AES-GCM of `{ body, tags, wordCount }`) plus `anchors` (link keys of files linked in the text) instead of `body`/`tags`. `locking.ts` locks/unlocks an existing entry: it fetches every version, encrypts or decrypts them here, and posts them with the text to `POST /api/{journal,writing}/:id/lock|unlock` (32 MB body limit on those routes and on reseal). Server: `entryService.lockEntry` refuses unless every readable version was sent, overwrites the versions (`versionRepo.rewrite`, size-limited batches), then replaces the entry's body, tags, excerpt and search terms in one transaction. A locked entry's searchable fields come from its title only; `locked: true` entries reject readable `body`/`tags`. A vault reset deletes locked entries, the entries key and every PIN device.
- Routes: `/`, `/inbox`, `/journal(/:id)`, `/writing(/:id)`, `/thinking`, `/reviews`, `/timeline`, `/ideas(/:id)`, `/money`, `/money/expenses`, `/money/ideas(/:id)`, `/tasks`, `/tasks/{upcoming,all,done,projects}`, `/tasks/projects/:id`, `/library` (books), `/library/books/:id`, `/documents` (query: `folder`, `view=recent|starred`, `q`, `doc`; the old `/library/documents` address redirects there), `/vault`, `/profile`, `/settings`. Note that tasks and projects live under `/tasks` even though the section is named "Projects & Tasks".

## Tests

`server/test/*.test.ts` run with vitest + supertest against the real Express app with the data layer replaced by in-memory fakes (`memory.ts`, `memory3.ts`, mocked in `setup.ts`; `statsRepo`/`activityRepo` fakes are in `memory3.ts` and aggregate over the other fake stores). No client tests exist.
