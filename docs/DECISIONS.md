# Decisions and constraints

Preserve these unless the owner explicitly changes them. Each has a reason.

1. **Browser never talks to Firebase.** All data and files go through the API. Keeps secrets server-side and permissions in one place (`permissions.ts`).
2. **Single-owner, registration closed.** `ALLOW_REGISTRATION=false`; the owner is created with `create-super-admin`.
3. **JWTs in httpOnly cookies, refresh tokens single-use and rotated.** Request auth reads no DB (cheap); disabled users are locked out at next refresh.
4. **No composite Firestore indexes.** Every query is one equality, `array-contains` or `orderBy`. Compound needs are solved with derived fields (`sortKey`) or in-memory filtering. Keeps setup zero-config and reads low.
5. **Maintain running totals transactionally** (`meta/*`, `FieldValue.increment`) so summaries cost one read.
6. **Search without a search service**: stored `searchTerms` + `array-contains`. Vault content is excluded from it.
7. **Money is integer minor units per currency, never converted.** Money-making ideas hold estimates that never count as income or expenses; the idea page links to real records instead of duplicating them. "Record as expense" is always an explicit action.
8. **Deadlines vs plans:** `dueDate` is a real deadline (only these can be overdue); `plannedDate` is "I'd like to do this that day" and never overdue.
9. **Edits never silently overwrite**: `rev` conflict detection on entries; the user chooses which version to keep.
10. **Vault is end-to-end encrypted in the browser.** AES-GCM vault key wrapped by a PBKDF2-SHA-256 (600k iterations) key from a separate passphrase; the key lives in memory only as a non-extractable `CryptoKey`; auto-lock after 10 min idle / 5 min hidden / reload / sign-out. Server stores only salt, wrapped key and ciphertext. Changing or resetting key material requires the account password. No local drafts of vault content; excluded from logs and search. It is deliberately not a password manager (accounts tab records where things are, not credentials). A lost passphrase is unrecoverable.
11. **Realtime by SSE, not websockets**, with a per-tab client id to ignore own echoes; Redis pub/sub only when scaled past one instance.
12. **Shared types are types only** (`shared/types.d.ts`, no runtime code), imported by relative path.
13. **One content frame for all pages** (`PAGE_FRAME`): sections share a left edge; widths vary only on the right.
14. **Tasks and projects stay under `/tasks`** even though the section is "Projects & Tasks" (renaming URLs would break links/bookmarks; only labels changed).
15. **Design identity**: quiet dark blue, serif + sans, small radii, no gamification, no card walls. Mobile first.
16. **Server tests use in-memory fakes** instead of Firebase, so they run anywhere with no credentials.
17. **Library folders are documents, files point at them** (`folderId`). Moving never touches Storage, so file ids, links, downloads and previews survive any reorganisation. A non-empty folder is never deleted silently: the API refuses (`409 FOLDER_NOT_EMPTY` with counts) unless the caller chooses `contents=move` (up a level) or `contents=delete`; the UI preselects keeping the contents.
18. **Lifetime statistics are derived, not counted up.** Counts and text totals are aggregation queries over the content itself (per-document `textWords`/`textChars` recomputed on save), so edits, deletes and imports can't leave them wrong. Active time counts a visible tab with no idle timeout (thinking and reading count), is deduplicated across tabs/devices on the server, and stores only durations and dates: no page contents, keystrokes, fingerprints or third-party analytics. Nothing about the vault is counted or shown: not its items, not time spent in it, not actions in it (decision 25).
19. **Words are linked to files inside the text itself.** A passage linked to a library file or folder is an ordinary Markdown link with an in-app address, `[my budget](doc:<id>)` / `[taxes](folder:<id>)` (`client/src/lib/anchors.ts`). It moves with the words as the text is edited and survives version history, copying and other devices with no offsets to keep in step. The server keeps a whole-item link in step with the words (`linkService.syncTextLinks`, run when a save adds or removes linked words and whenever an entry's links are listed): a file or folder linked from the text is linked to the entry, so the file lists it under "Linked", and the link goes again once no words point at it. Removing or unlinking the words always removes that file's link to the entry, however it was made. Otherwise links carry a `source`: `text` ones follow the words; `manual` ones ("Link", quote → book, idea → project) to files the text never linked are left alone. Links stored without a source before 2026-10-29 11:02:47 UTC (when linked words shipped) count as manual; later ones as text.
20. **Stored files are cached by the browser for good** (`Cache-Control: private, max-age=31536000, immutable`): an upload always gets a new id and the bytes never change, only the metadata does. Signing out sends `Clear-Site-Data: "cache"` so they don't stay on the device.
21. **A belief is written around where you stand.** Its positions are a dated list, newest first, above the optional Markdown notes: the latest is open and earlier ones are folded to one line; any can be opened, edited in place (autosaved) or deleted. A new position starts blank and is only kept once something is written in it. All of it uses the same type as the note's text. A belief can be created from a position alone (`perspectives` on create), and its list excerpt is the latest position.
22. **Formatted writing, stored as Markdown.** Entries are edited in a Tiptap (ProseMirror) editor that shows the text as it reads (`features/entries/RichEditor.tsx`, loaded on demand), but bodies stay Markdown in the database, so nothing else (search, excerpts, version history, the reading view) changed. Before using it for a text, the editor checks that what it would save renders exactly like the original (with its own `marked` instance; footnotes are refused outright, since only the reading view knows them). If not (images, raw HTML, footnotes), that entry is edited in the plain Markdown textarea, so formatting it can't represent is never lost. Anyone can switch to plain Markdown for good (⋯ menu, per device). Known normalisation on the first edit: `_italic_` becomes `*italic*`, loose lists lose their blank lines, tables are re-padded.
23. **Undo takes back one action, in the text only.** Both editors keep their own history in memory for as long as the entry is open (`RichEditor`: ProseMirror's history plus `UndoSteps`; `MarkdownEditor`: `textHistory.ts`, since the browser's textarea undo breaks whenever the text is set from code and can't be driven from a button). Typing in quick succession (500 ms) is one step; formatting (toolbar or shortcut), a link, an unlink and a restored version or draft are each a step of their own. An edit that arrives from another device clears the history (`historyKey` from `useEntryEditor`), so undo never quietly reverts that device's work. Undoing back to the text the editor opened with gives back that exact text, so it isn't saved again. The title, tags and date keep the browser's own undo; switching between formatted and plain Markdown starts a fresh history.
24. **Usage is measured, not judged.** Time per section is the visible-tab time of the existing active-time rule, split by the address on screen (`client/src/lib/sections.ts`, one section per area of the navigation, Projects and Tasks apart, Income/Expenses/Money-making ideas apart; dialogs and query strings never make a section). A visit is an arrival from another section or after 30 minutes away, so reloads and extra tabs don't inflate it. Meaningful actions are counted on the server after success, as distinct item ids per action per local day (an edit on the creation day counts only as created), stored in the same day documents and totals as time so one recount rebuilds both. Only durations, dates, section keys, counts and item ids are kept; never content, keystrokes, devices or location. The profile shows figures and comparisons only where the data was recorded in full, and offers no verdicts or recommendations: a rarely opened section can still matter.
25. **The vault leaves no trace in statistics.** The profile never shows anything about it: no item count, no time, no visits, no actions. Time on `/vault` isn't recorded at all (not even in the total), its services record no actions, and the stats code has no `vault` key. Even a count of items would say something about what is kept there. The lock screen is a plain form (a lock icon, "Locked", the passphrase field, when it locks again), with no mock safe-door styling or cipher names.
26. **The installed app never reloads under the owner's hands.** A new version is applied only in the first seconds after launch or on pull to refresh, and pull to refresh is off while anything has unsaved work, so an update can't discard a draft. The query cache is kept on the device for a week so the app opens at once and offline, but it belongs to the session: it is dropped on sign-out or when the server finds no session, and the vault and open editor texts are never part of it.
27. **Locked entries are encrypted in the browser and opened with a per-device PIN that the server checks** (how: decision 28). Lock before the first save and the server never receives the text; lock later and the browser re-sends the text and every version encrypted, and the server overwrites every readable copy (entry body, tags, excerpt, search terms, versions) before the lock is accepted. The title stays readable by choice, for lists and search. Version labels and word counts are sealed too, and encrypted entries record no actions. Time on screen with one open (or at its PIN prompt) is counted in its section (Journal or Writing) like any page, at the owner's request (2026-11-17); only the duration, date and section are stored, never anything about the entry. What stays readable: title, journal date, created/edited times, the save counter and version times, pinned/archived, the size of the ciphertext, and the ids of linked files. The key stays in memory only and locks with the same rules as the vault; an open editor saves (encrypted) before it locks.
28. **The PIN never protects a key on its own; the entries key has its own key.** Encrypted entries use a random entries key, stored on the server only encrypted with the vault key (so the passphrase can always recover it); the vault key never stays on a device. On a device, the entries key sits in a box that needs the device's data (the box and a salt), a random server half that only the server keeps, and the PIN: PBKDF2(PIN, device salt) gives a check value (sent; the server stores its SHA-256) and a wrapping part (never sent), and the box opens with HKDF(wrapping part + server half). The server releases the server half only for the right check value and deletes it after five wrong PINs, so a copy of a device's storage can't be used to try PINs offline, and a copy of the database opens nothing (no box, no salt). Cost: opening encrypted entries needs a connection. Devices are listed in Settings and can be removed. Entries sealed by the first version (vault key, no key id in the box) are re-sealed in the browser the first time the passphrase is entered (`migrateEntries.ts`, `POST /:id/reseal`), and the old on-device record (vault key behind the PIN) is deleted on load. Before this, the first version kept the vault key on the device behind the PIN alone: anyone able to copy the browser's storage could have found the PIN by trying all of them, and the vault key with it; changing the passphrase does not change the vault key.
29. **The PIN opens one encrypted entry at a time.** Entering the PIN opens the entry it was asked for (`requestUnlock({ scope })`, `isOpen(id)`); every encrypted entry not yet opened needs the PIN first, even while others are open. An opened entry stays open, also after leaving it, until the next lock (Lock now, 10 minutes without activity, 5 minutes in the background, reload, sign-out), which closes all of them. So a phone taken with entries open gives access to those entries only. The key itself is shared by all entries; the boundary is in the app, which is what matters for someone holding the phone. Lists show an amber open lock for opened entries and a closed lock for the others.
30. **Miniapps are apart from the site, on purpose.** Small or temporary features go in `client/miniapps/` instead of new pages: each is a folder found at build time, uses only the toolkit `@miniapp/sdk` (lint-enforced both ways), and stores one JSON value per account through a generic API, so a new miniapp needs no server or site change and removing one is deleting its folder. They are switched on in a Store (data kept when switched off, until deleted). The miniapps screen is deliberately phone-like, the one exception to the small-radius and no-effects rules (asked for by the owner, 2026-11): squircle app icons like a phone's (2026-11-14, after the owner found the first shaded version "dead"): clear colours or two-colour gradients, large bold glyphs, no shadows or bevels; frosted widget cards and folders, red badges, an opening animation that grows the icon into the screen, a frosted bottom bar tinted to the wallpaper (for a picture, to its measured brightness), tiles arranged by dragging. Wallpapers stay the site's own background (default), quiet solids or the owner's picture. Outside that screen (and the Store's icons) nothing changes. Inside, apps use the site's colour tokens and type. Miniapp data is not encrypted and not part of the profile's statistics. Recipe: `client/miniapps/README.md`.
